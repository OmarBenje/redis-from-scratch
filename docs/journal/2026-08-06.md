## Make

**La tabulation.** Les lignes de recette commencent par une vraie tabulation, jamais des espaces. `missing separator` veut **toujours** dire ça. Pour vérifier : `cat -A Makefile`, les tabulations s'affichent `^I`.

**`:=` plutôt que `=`.** `=` est différé (la valeur est calculée à l'usage), `:=` est immédiat (calculée à la définition). `:=` par défaut : comportement prévisible.

**Une cible, c'est ce qui *sort*.** Pas un fichier qu'on possède, un fichier qu'on fabrique. Les `.c` sont les feuilles du graphe, l'exécutable la racine. Un `.c` ne peut jamais être une cible principale.

**`$@`, `$<`, `$^`** = la cible, la première dépendance, toutes les dépendances. Évitent de répéter les noms de fichiers.

**`.PHONY`** protège les cibles qui ne sont pas des fichiers. Sans ça, le jour où un fichier nommé `clean` existe, `make clean` répond `is up to date` et ne fait plus rien — sans erreur.

**Les dépendances passent avant la recette.** `fclean: clean` → make exécute la recette de `clean`, *puis* celle de `fclean`. Même mécanisme que `server: main.o`.

**Une variable ne s'applique que là où on l'écrit.** Définir `LDFLAGS := ...` en haut ne fait rien ; il faut `$(LDFLAGS)` dans la recette. Erreur commise en vrai sur ASan.

**⚠️ Le piège silencieux : une règle de motif dont une dépendance n'existe pas est *jetée sans un mot*.** Make se rabat alors sur sa règle intégrée `%.o: %.c`, qui ne connaît aucun header. Le suivi des `.h` ne marche plus, et rien ne prévient.

Signature visible dans la forme de la commande :
```
gcc ...   -c -o main.o main.c      ← la règle intégrée de make
gcc ... -c main.c -o main.o        ← la mienne, avec $< et $@
```
`make -r` (désactive les règles intégrées) fait apparaître le vrai problème.

**Conséquence :** `SRCS` et `HEADERS` = l'inventaire de ce qui est **sur le disque maintenant**, pas une liste de souhaits. Un `.c` déclaré trop tôt → erreur franche. Un `.h` déclaré trop tôt → panne muette (bien pire).

**Le bug des headers** (§11 du cours) : modifier un `.h` sans que make recompile → des `.o` qui ne s'accordent plus sur la taille d'un `struct` → segfault sans avertissement. Réflexe quand un comportement devient inexplicable après avoir touché un `.h` : `make re`.

**`make -n`** affiche les commandes sans les exécuter. Premier réflexe quand make ne fait pas ce qu'on croit.
**`make -B`** force la reconstruction complète.
**`$(info $(VAR))`** = printf de Makefile, pour inspecter une variable.

**Chaque ligne de recette = un shell neuf.** Donc `cd src` sur une ligne puis `gcc` sur la suivante ne marche pas. Il faut `cd src && gcc ...`.

## Compilation C

**Les 4 étapes de gcc :** préprocesseur → compilation → assemblage → **édition de liens**. La coupure entre les deux dernières est ce qui rend make utile.

**Un `.o` est du code machine *incomplet*** : les appels aux fonctions définies ailleurs sont des trous, remplis par le linker.

```sh
file server.o    # "relocatable" = incomplet
file server      # "executable"  = complet
```

**`-o`, `-c`, `-g` répondent à trois questions différentes :**

| Flag | Question |
|---|---|
| `-o` | **où** je mets le résultat |
| `-c` | **jusqu'où** je vais (arrêt au `.o`) |
| `-g` | **quoi** je mets dedans (infos de debug) |

D'où la structure du Makefile : le « quoi » va dans `CFLAGS` (identique partout), le « jusqu'où » et le « où » restent dans les recettes.

**`-g` change tout au debug.** Sans lui : `0x401136 in ?? ()`. Avec : `store_get (s=0x0, key="foo") at store.c:42`. Aucun coût à l'exécution, juste un binaire plus gros.

**⚠️ Ne jamais taper `gcc -o fichier.c fichier.c`** — gcc écrase la source avec l'exécutable. Code perdu.

**Le nom de sortie n'a aucun lien avec le nom de la source.** `gcc -o toto server.c` marche. Dans `gcc -o server server.c`, les deux mots désignent deux fichiers différents ; c'est l'habitude qui les fait coïncider.

### Header ≠ bibliothèque

Deux choses distinctes, à deux étapes distinctes :

| | Apporte | Étape |
|---|---|---|
| `#include <sys/socket.h>` | le **prototype** + les constantes | compilation |
| `-lm`, `-lpthread` | le **code** de la fonction | linking |

| Message d'erreur | Étape | Ce qui manque |
|---|---|---|
| `implicit declaration of function 'socket'` | compilation | le **header** |
| `undefined reference to 'socket'` | **linking** | la **bibliothèque** |

**La libc est liée automatiquement par gcc.** D'où : aucun `-l` pour `socket`, `printf`, `close`. Vérifiable avec `ldd server` (`libc.so.6` apparaît sans qu'on l'ait demandée).

Exceptions à lier explicitement : `-lm` (maths), `-lpthread` (threads), `-ldl`. C'est à ça que sert `LDLIBS` dans le Makefile.

Un `#define` comme `AF_INET` ne peut venir **que** d'un header — aucune bibliothèque ne peut le fournir, ce n'est pas du code.

*(Culture : sur Solaris il fallait `-lsocket -lnsl`. Pas sur Linux — ne pas recopier ces flags vus dans de vieux tutos.)*

**ASan doit être passé aux DEUX étapes** (`CFLAGS` et `LDFLAGS`). À la compilation gcc insère des appels à `__asan_init` & co ; au linking il faut fournir la bibliothèque qui les contient. Ne le mettre qu'à la compilation → cascade d'`undefined reference to '__asan_*'`.

## Langage C

**⚠️ La portée d'un identificateur commence à la fin de son *déclarateur*, pas de l'instruction.**

```c
int socket = socket(AF_INET, ...);   // erreur : le "socket" appelé est déjà la variable int
```
Le déclarateur `int socket` se termine avant le `=`. Même piège que `int x = x + 1;`.

→ Nommer les fd distinctement dès le départ : `listen_fd` (écoute) et `client_fd` (retour d'`accept`). Deux fd, deux `close()`.

**Littéral composé** (C99) : `&(int){1}` crée un objet anonyme de type `int` valant 1, et en prend l'adresse. Durée de vie = le bloc englobant. C'est ce qui rend l'adresse valide (`&1` serait illégal).

Forme explicite préférable pour l'instant :
```c
int yes = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes));
```
**`sizeof(yes)` plutôt que `sizeof(int)`** : suit automatiquement le type de la variable. Écrire le type à la main devient un bug silencieux si le type change.

**Un `;` après une accolade fermante** est une instruction vide, inoffensive — mais `if (x == 1);` fait exécuter le bloc suivant **inconditionnellement**.

## `perror` et `errno`

`perror("socket")` affiche sur **stderr** : `socket: Permission denied`. Convention : lui passer le nom de l'appel qui a échoué.

Il ne fait que lire `errno` (variable globale renseignée par le noyau) et le traduire en texte.

**Trois règles :**

1. **Détecter l'échec par la valeur de retour, jamais par `errno`.** `errno` n'est jamais remis à zéro en cas de succès — il ne veut dire quelque chose qu'*après* un échec avéré.
2. **Appeler `perror` immédiatement.** Presque n'importe quel appel de fonction peut écraser `errno`, y compris un `printf` intercalé.
3. **`perror` n'arrête pas le programme.** Il affiche, point. Sans `return 1;` derrière, on enchaîne sur `bind(-1, ...)` et on obtient une cascade d'erreurs dont seule la première compte.

**stderr plutôt que stdout**, pour pouvoir séparer les canaux :
```sh
./server > sortie.txt      # les erreurs restent à l'écran
./server 2> erreurs.txt    # les erreurs seules vont au fichier
```

**Variante :** `strerror(errno)` (`<string.h>`) rend juste la chaîne, pour composer un message plus riche :
```c
fprintf(stderr, "socket(port %d): %s\n", 6379, strerror(errno));
```

## Codes de retour et `$?`

`$?` = code de retour de la dernière commande. C'est exactement le `return` de `main` (ou `exit(n)`).

`0` = succès, non nul = échec. Une seule façon de réussir, plusieurs de rater.

| Code | Sens |
|---|---|
| `0` | succès |
| `1` | échec générique |
| `126` | trouvé mais pas exécutable |
| `127` | commande introuvable |
| `134` | `abort()` — c'est ainsi qu'ASan termine |
| `139` | **segfault** (128 + signal 11) |

`139` = segfault, avant même de lire quoi que ce soit.

**Le shell s'en sert :** `make && ./server` ne lance le binaire que si la compilation a réussi — évite de tester l'ancien exécutable par erreur.

**Make s'en sert aussi :** `make: *** [Makefile:14: server] Error 1` — le `1` est le code rendu par gcc. C'est aussi pourquoi `rm -f` dans `clean` : sans `-f`, `rm` échoue sur un fichier absent et fait planter la cible.

**⚠️ `$?` est écrasé par chaque commande, y compris `echo`.** Le lire immédiatement, ou le ranger : `code=$?`.

## Sockets

**`socket(domain, type, protocol)`** — trois questions :

| Argument | Question | Choix ici |
|---|---|---|
| `domain` | quelle famille d'adresses ? | `AF_INET` (IPv4) |
| `type` | quelle sémantique de transport ? | `SOCK_STREAM` (TCP, flux ordonné fiable) |
| `protocol` | lequel exactement ? | `0` |

`0` ne veut pas dire « TCP » mais **« le protocole par défaut pour cette combinaison »** — qui se trouve être TCP ici. Le même `0` donne UDP avec `SOCK_DGRAM`.

`AF_INET` va de pair avec `struct sockaddr_in` (le `_in` = *internet*).

**`setsockopt(fd, level, optname, optval, optlen)`** — cinq arguments parce que la fonction est **générique** : chaque option a son propre type (`int`, `struct linger`, `struct timeval`). D'où le `void *` + la taille.

Le `level` se déduit du préfixe de l'option : `SO_*` → `SOL_SOCKET`, `TCP_*` → `IPPROTO_TCP`, `IP_*` → `IPPROTO_IP`.

**`SO_REUSEADDR`** contourne l'état `TIME_WAIT` (~60 s pendant lesquelles le noyau retient le port après fermeture, au cas où des paquets en retard traîneraient). Sans elle : `bind: Address already in use` à chaque relance rapide. **À poser avant `bind()`** — elle modifie le comportement de `bind`, après elle ne sert à rien.

**Attention aux conventions de retour différentes :** `socket()` rend un fd (`-1` = échec), `setsockopt()` rend `0` en cas de succès. Toujours lire la section **RETURN VALUE** du `man`.

## Outils

**`man 2 socket`** — la section `2` = appels système. Sans le `2`, on peut tomber sur autre chose. Sections utiles : **SYNOPSIS** (les includes à mettre !) et **RETURN VALUE**.

**`strace`** — voir les appels système réellement passés au noyau, décisif pour du code réseau :
```sh
strace -e trace=socket,setsockopt,close ./server
```
```
socket(AF_INET, SOCK_STREAM, IPPROTO_IP) = 3
setsockopt(3, SOL_SOCKET, SO_REUSEADDR, [1], 4) = 0
```
On y lit le fd rendu, le succès, et `[1], 4` = la valeur pointée par `&(int){1}` vue depuis le noyau.

**Forcer un échec pour tester ses `perror`** — sinon on ne sait pas s'ils marchent :
```sh
( ulimit -n 3 ; ./server )    # 0,1,2 déjà pris → socket() échoue avec EMFILE
# → socket: Too many open files
```

**⚠️ ASan pollue la sortie de `strace`.** Son initialisation passe des centaines d'appels système (`mmap`, `close`…), qui noient les miens. Filtrer sur ce que je cherche vraiment plutôt que sur le nom de l'appel :
```sh
strace ./server 2>&1 | grep -E 'AF_INET|SO_REUSEADDR'
```
`strace -e trace=close` est inutilisable ici : des dizaines de `close(3) = 0` d'ASan avant le mien.

**`ldd server`** — les bibliothèques dynamiques réellement liées.

**`ss -tlnp | grep 6379`** — vérifier qu'un `bind`/`listen` a pris (à utiliser bientôt).

## Git

**`.gitignore`** : on versionne ce qu'on écrit à la main, on ignore ce que `make` fabrique (`*.o`, `*.d`, l'exécutable, `.idea/`, `vgcore.*`).

**Le slash initial ancre à la racine du dépôt.** `/server` n'ignore que l'exécutable ; `server` ignorerait aussi un futur dossier `src/server/`. Réflexe pour les noms de binaires.

**⚠️ `.gitignore` n'agit que sur les fichiers non suivis.** Un fichier déjà commité continue d'être suivi. Il faut `git rm --cached <fichier>` (retire du suivi, garde le fichier sur le disque).

## Divers

**Descripteurs de fichiers :** 0, 1, 2 sont pris (stdin, stdout, stderr). Le premier fd qu'on obtient vaut donc `3` — c'est ce qui rend le test de l'étape 1 vérifiable à l'œil.

**Méthode de travail réseau : un appel système à la fois.** Écrire, compiler, lancer, vérifier — puis le suivant. Écrire les six d'un coup, c'est une soirée à chercher lequel a lâché.
