# Journal — 7 août 2026

Séance : boucle `read()`, fin de l'étape 1. ⚠️ = piège silencieux.

---

- `read(fd, buffer, taille)` a **trois** issues à gérer séparément : `> 0` (octets reçus, peut être moins que demandé — TCP est un flux, pas des messages), `0` (le client a fermé, fin normale), `-1` (erreur réelle).
- `ssize_t` (signé) pour le retour de `read`, pas `size_t` : `-1` doit être représentable.
- **⚠️ `read()` ne termine pas le buffer par `\0`.** Pour l'afficher comme texte, utiliser le nombre d'octets réellement lus (`rc`), jamais la taille du buffer.
- Taille de buffer sans enjeu précis : `4096` (une page mémoire) est un choix courant. Si le client envoie plus, `read()` est simplement rappelé — pas de perte.
- `%zd` pour afficher un `ssize_t` avec `printf`.
- Le serveur actuel ne boucle pas sur `accept()` : une connexion traitée, puis le programme se termine. `Connection refused` sur un client qui arrive après = normal, pas un bug (rien n'écoute plus).
- Test validé avec un vrai client Redis : `redis-cli -p 6379 ping` envoie 14 octets, exactement `*1\r\n$4\r\nPING\r\n` (protocole RESP). `redis-cli` reste bloqué en attente de réponse : normal tant que `write()` n'existe pas.
- **Étape 1 terminée** : socket → setsockopt → bind → listen → accept → read() (3 cas) → close × 2, zéro warning sous `-Wall -Wextra -Werror` + ASan/UBSan.
