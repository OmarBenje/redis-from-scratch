- `read(fd, buffer, taille)` a **trois** issues à gérer séparément : `> 0` (octets reçus, peut être moins que demandé — TCP est un flux, pas des messages), `0` (le client a fermé, fin normale), `-1` (erreur réelle).
- `ssize_t` (signé) pour le retour de `read`, pas `size_t` : `-1` doit être représentable.
- **⚠️ `read()` ne termine pas le buffer par `\0`.** Pour l'afficher comme texte, utiliser le nombre d'octets réellement lus (`rc`), jamais la taille du buffer.
- Taille de buffer sans enjeu précis : `4096` (une page mémoire) est un choix courant. Si le client envoie plus, `read()` est simplement rappelé — pas de perte.
- `%zd` pour afficher un `ssize_t` avec `printf`.
- Le serveur actuel ne boucle pas sur `accept()` : une connexion traitée, puis le programme se termine. `Connection refused` sur un client qui arrive après = normal, pas un bug (rien n'écoute plus).
- Test validé avec un vrai client Redis : `redis-cli -p 6379 ping` envoie 14 octets, exactement `*1\r\n$4\r\nPING\r\n` (protocole RESP). `redis-cli` reste bloqué en attente de réponse : normal tant que `write()` n'existe pas.
- **Étape 1 terminée** : socket → setsockopt → bind → listen → accept → read() (3 cas) → close × 2, zéro warning sous `-Wall -Wextra -Werror` + ASan/UBSan.

## Étape 2 — write() et parsing RESP

- `write(fd, buf, count)` : même famille que `read()`, trois issues (`>0`, `0`, `-1`). En pratique `0` n'arrive jamais si `count > 0` (contrairement à `read()` où `0` = fin de flux) — code mort mais gardé par rigueur.
- **⚠️ `sizeof(buffer)` ≠ quantité de données valides.** Après `read()`, seuls les `rc` premiers octets du buffer sont pertinents ; envoyer `sizeof(buffer)` avec `write()` renvoie des ordures en plus des vraies données.
- `sizeof` sur un **tableau** (`char msg[] = "..."`) donne la bonne taille ; sur un **pointeur** (`char *msg = "..."`), donne la taille du pointeur (8), pas de la chaîne. `strlen` marche dans les deux cas.
- Protocole RESP (requêtes) : `*N\r\n` = tableau de N éléments, puis pour chacun `$L\r\n<L octets>\r\n` (bulk string de longueur L). Auto-descriptif : pas besoin de deviner où une chaîne s'arrête.
- `strtol(nptr, &endptr, base)` : convertit du texte en `long`. Écrit dans `endptr` (via son adresse) le pointeur vers le premier caractère non consommé — évite de boucler à la main pour trouver la fin d'un nombre.
- **`endptr` est un paramètre de sortie pur** : pas besoin de l'initialiser avant l'appel, `strtol` l'écrase avant qu'on le lise (même logique que `buffer` avant `read()`). Différent de `addr_len` avant `accept()`, qui est entrée *et* sortie : là il fallait l'initialiser.
- `%ld` pour afficher un `long` avec `printf`, pas `%lf` (réservé à `double`) — erreur détectée par `-Werror=format=`, message gcc très clair.
- **⚠️ `\r` et `\n` sont chacun UN SEUL caractère** (codes ASCII 13 et 10), malgré leur écriture à deux symboles dans le code source. Entre `fin` (pointeur sur le `\r` rendu par `strtol`) et le prochain élément RESP, il y a donc 2 octets à sauter (`fin + 2`), pas 1.
